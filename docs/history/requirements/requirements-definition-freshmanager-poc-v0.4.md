# 요구사항 정의서 v0.4 — 프레시매니저 유동판매 추천 서비스 (데이터 타당성 PoC)

> **역사 문서**  이 문서는 PRD v1.0 이전의 요구사항 기준선으로 보존한다. 현재 제품 기준은
> [`docs/product/FreshManager_PRD_v1.0.md`](../../product/FreshManager_PRD_v1.0.md),
> 현재 기술 기준은
> [`docs/engineering/FreshManager_TRD_v1.0.md`](../../engineering/FreshManager_TRD_v1.0.md)를 따른다.
> 이 문서의 과거 수집 순서나 운영 예시는 현행 실행 승인을 의미하지 않는다.

*v0.3 대비 "유동인구≠매출" 원칙을 데이터 차원에서 보강(상권현황 추가)하고, 날씨 시점 원칙(예보값 vs 실측값)을 명시했다. 외부 제안 중 수집 메타데이터 15개 필드·6주 연장·교통/행사 데이터는 1인 운영 규모에 맞게 선별 반영했다(9번 비기능요구사항 참조). 이 문서는 이전 버전 없이 단독으로 읽히도록 작성됐다. v0.1~v0.3은 폐기하지 않고 이전 버전으로 보관.*

**정합성 보정일: 2026-07-20** — 최소 수집 메타데이터를 공식 8개 계약으로
정렬했다. 제품 범위, 기능 요구사항과 Gate A·B·C는 변경하지 않았다.

## 1. 개요

**문서 목적**: 데이터 타당성 PoC 단계의 요구사항을 구체화한다. 이 문서가 정의하는 "요구사항"은 서비스 기능이 아니라 PoC 분석 파이프라인의 요구사항이다.

**제품 정의**: (장기 비전) 프레시매니저의 유동판매 위치·시간 추천 서비스. (v0.4, 현재 범위) 그 전제조건인 데이터 타당성 검증 산출물.

**비전과 주요 전제**: 야쿠르트 단일 상품, 오피스 상권형 담당구역(1차 후보 여의도), hy 비제휴 PoC. 서울시가 이미 Seq2Seq AI 기반 12시간 예측을 제공 중이며, 이는 매뉴얼·언론보도·통신사 보도자료 세 개 독립 출처로 확인됐다.

---

## 2. 배경 및 문제 가설

"프레시매니저는 위치 선정을 경험에만 의존해 매출 기회를 놓친다"는 것은 본인이 제시한 **문제 가설**이며, 아직 인터뷰나 데이터로 확인된 사실이 아니다. 이번 PoC는 이 가설의 전제조건(유동인구가 예측 가능한 수준인지)만 검증하며, 문제 가설 자체의 검증은 후속 인터뷰(Gate C, 12번 참조) 몫이다.

---

## 3. 목표 및 판정 기준

데이터 가설·예측 가설·비관행 피크 존재 여부 세 가지만 이번 PoC가 직접 판정한다.

## 4. 대상 사용자 및 PoC 운영자

**장기 제품 목표 사용자**: 오피스 상권 담당구역에서 정기배송 이후 유동판매를 수행하는 프레시매니저. (계약 형태는 공식자료·현장 인터뷰로 재검증할 별도 항목이라, PoC 시스템 사용자 선정 조건에서는 제거함 — P0 반영)

**v0.4 PoC 시스템 사용자**: 데이터 수집·검증·분석·리포트 작성을 수행하는 분석 담당자(본인). PoC 단계에서 시스템을 실제로 쓰는 사람은 프레시매니저가 아니라 이 분석 담당자다.

**PoC 운영자**: 본인 1인. hy와 공식 소통 채널 없음(비제휴), 본인 명의 공공 API 키로 수집. Claude는 분석 설계·코드 자문 역할이며 실제 API 호출은 운영자 환경에서 수행.

## 8. 데이터 요구사항

**저장 구조(P0 전면 수정)** — 이전 "동일 시각 중복 수집 시 최신값 우선" 규칙은 폐기한다. 같은 미래 시점(예: 오후 3시)에 대한 예측값이 오전 9시·정오·오후 2시에 각각 다르게 나올 수 있는데, 최신값으로 덮어쓰면 리드타임별 예측 성능을 비교할 수 없기 때문이다.

**A. 원본 응답** (수정·덮어쓰기 금지)

원본 응답과 함께 다음 최소 수집 메타데이터를 기록한다.

| 필드 | 설명 |
|---|---|
| request_id | 요청 고유 ID |
| area_code | 장소 코드 |
| endpoint_name | 실제 URL이 아닌 논리적 API 이름 |
| requested_at | 호출 시각 |
| received_at | 응답 수신 또는 요청 실패 확인 시각 |
| http_status | 응답 상태 |
| collection_status | 수집 처리 결과 |
| raw_file_path | 저장된 원본 응답 파일 경로 |

`raw_payload`는 메타데이터가 아니라 수정하지 않고 보존하는 원본 응답이다.
원본 응답의 저장 위치는 `raw_file_path`로 추적한다. `parser_version`은 최소
수집 계약에 포함하지 않으며 향후 정규화·분석 데이터 저장 단계에서 별도 검토한다.

**B. 현재 관측값** — 고유키: `area_code + population_reference_time + request_id`(수정 응답이 리비전으로 남으려면 request_id가 있어야 함 — source_schema_version은 고유키가 아닌 일반 메타데이터로 보관)

**C. 예측값** — 고유키: `area_code + forecast_snapshot_time + forecast_target_time + request_id`, 파생 필드 `lead_time_minutes = forecast_target_time − forecast_snapshot_time`(실제 API 필드명이 `forecast_issued_at`으로 확인되기 전까지는 중립적 명칭인 `forecast_snapshot_time`을 사용)

이 구조가 있어야 1·3·6시간 리드타임별 예측 성능을 재현 가능하게 비교할 수 있다.

**품질 규칙(P0 수정)**: 원본 응답은 모두 불변 저장한다. 동일 기준시각의 수정 응답이 발생해도 삭제하지 않고 request_id로 구분된 리비전으로 보존하며, 분석용 정규화 테이블은 최신 리비전을 기본값으로 쓰되 변경 이력은 추적 가능해야 한다.

**D. 상권현황 스냅샷(v0.4 신규)** — 고유키: `area_code + commerce_reference_time + request_id`. 필드: 상권 활동단계(한산/보통/바쁨/분주함), 과거 4주 평균 대비 상태, 데이터 제공 여부(82장소 미포함 시 결측 처리), 인구 데이터와의 기준시각 차이(정렬용). 결과 표기는 반드시 "소비활동 대리변수"로 한정하며 실제 hy 매출로 서술하지 않는다.

**E. 날씨 스냅샷(v0.4 신규)** — 실측값과 예보값을 별도 테이블로 분리 저장. 예보값 고유키: `area_code + forecast_snapshot_time + forecast_target_time + request_id`(예측값과 동일한 원칙). 예보값이 없다고 임의로 실제값을 대신 채우지 않는다.

**보관 정책**: 원본·정규화 데이터는 PoC 전체 수집기간 동안 보관하며 최소 보관기간은 5주(진행 일정과 일치). 최종 리포트 작성 완료 전까지 삭제하지 않는다.

**메타데이터 범위에 대한 원칙(v0.4)**: 외부 제안은 수집실행 메타데이터로 15개 필드(스키마 지문, 계획중단 여부 구분 등)를 제시했으나, 1인 운영 PoC 규모에는 과하다고 판단해 반영하지 않는다. 위 공식 8개 계약(request_id·area_code·endpoint_name·requested_at·received_at·http_status·collection_status·raw_file_path)을 유지하며, 실제 운영 중 필요성이 확인될 때만 필드를 추가한다(9번 비기능요구사항의 유지보수성 원칙과 연결).

- FR-2: 예측 발행시각·목표시각 모두 저장됨 / 목표시각의 후속 관측값과 자동 매칭됨 / 1·3·6시간 리드타임 계산됨 / 후속 관측값이 없으면 "평가 불가"로 명시적 처리됨

- FR-7(상권현황, v0.4 신규): 상권 기준시각과 인구 기준시각이 각각 저장됨 / 상권 활동단계가 수집됨 / 데이터 미제공을 "한산" 등으로 임의 변환하지 않고 결측으로 표시됨 / 인구·상권 자료 간 시각 차이가 기록됨 / 결과에는 "실제 hy 매출"이 아닌 "소비활동 대리변수"로 표시됨

**B. PoC 평가 기준(시간 경과에 따라 단계적으로 판단)**

| 시점 | 평가 |
|---|---|
| 1주 | API·스키마·수집기 안정화 확인 |
| 2주 | 결측·지연 기준선, 잠정 패턴 확인 |
| 3~4주 | 반복 패턴 누적(B1 평가) |
| 4주 종료 | 동일 요일·시간 기준선(B2) 생성 완료 |
| 5주 | B2 기준선을 이용한 전향적 평가, 최종 분석·리포트·판정 |
| 5주 종료 | 표본 부족이 실제로 확인될 때만 1주 연장 결정 |

1주 분량만으로 예측 성능을 최종 판단하지 않는다 — 평일 반복은 보이지만 주간 변동성은 4주는 봐야 확인된다.

**일정 연장에 대한 원칙(v0.4)**: 외부 제안은 "4주 기준선 완성 후 5주차를 그 기준선으로 평가"하는 것이 방법론적으로 더 엄밀하다는 이유로 6주로 미리 늘리자고 했다. 방법론은 맞지만, 미리 늘리지 않는다 — 5주차 시점에 기준선이 실제로 부족하다고 확인되면 그때 1주를 연장한다. 사전에 일정을 늘리는 것 자체가 검증되지 않은 가정에 계획을 맞추는 것이기 때문이다.

## 12. Go/No-Go 기준 (P0 전면 재설계)

v0.2의 "예측 개선+피크 존재 → 바로 Phase 5" 구조는 **단계를 두 번 건너뛴 판단**이었다. 데이터가 예측 가능하다는 것은 프레시매니저가 실제로 문제를 겪는지, 담당구역 내 이동이 가능한지, 유동인구와 야쿠르트 구매가 관련되는지를 전혀 증명하지 않는다. 게이트를 4단계로 분리한다.

| 게이트 | 확인 내용 | 시점 |
|---|---|---|
| **A. 기술적 데이터 타당성** | 안정적 수집 가능한가 / 예측 필드 확보 가능한가 / 서울시 예측이 기준선보다 나은가 / POI 공간 범위가 명확한가 | **이번 v0.4** |
| **B. 인구·소비 시간패턴 타당성**(v0.4 재정의 — 상권현황 반영) | 비관행 시간대 인구 피크가 존재하는가 / 인구 증가와 카드소비 활동단계가 함께 변하는가, 아니면 인구만 늘고 소비는 정체되는가 / 판매원이 움직일 리드타임이 있는가 / 패턴이 특정 하루가 아니라 반복되는가 | **이번 v0.4** |
| C. 사용자 문제 타당성 | 실제로 위치·시간 선택에 어려움이 있는가 / 데이터 추천이 경험보다 가치 있는가 / 담당구역·재고·배송종료시간 제약은 무엇인가 | 후속 인터뷰 |
| D. 현장 성과 타당성 | 추천 장소로 이동하는가 / 고객 접촉·판매가 증가하는가 | 후속 실증 |

**v0.4 판정표**

Gate B가 통과해도 도달 가능한 결론은 "여의도에서 인구와 일반 소비활동의 시간패턴이 후속 검토에 활용할 수준으로 존재한다"까지다. 카드소비는 실제 야쿠르트 구매가 아니므로 "이 시간대에 야쿠르트가 잘 팔린다"는 결론은 이 PoC로 낼 수 없다.

| 결과 | 판정 | 다음 행동 |
|---|---|---|
| 데이터 안정 + 예측 활용 가능 + 비관행 패턴 존재 | Gate A·B 통과 | 프레시매니저 인터뷰(Gate C)와 현장 후보지 조사로 진행 |
| 데이터 안정 + 예측 개선 없음 + 패턴 존재 | 조건부 통과 | 예측 없이 현재 혼잡·반복 패턴 활용 가능성 검토 |
| 데이터 안정 + 비관행 피크 없음 | **시간확장 가설만 기각** | 서비스 전체를 No-Go 처리하지 않는다. "기존 점심 피크 안에서 더 적합한 위치를 고르는" 가설은 별도로 남아 있어 Gate C에서 확인 |
| 데이터 불안정 | Gate A 미통과 | API·수집기·대체 데이터 원인 분리 후 재판정 |
| POI 공간 단위가 너무 넓음 | 서비스 연결성 미충족 | S-DoT·현장 관찰·지점 데이터 보강 가능성 검토 |

## 14. API 신청 실행 가이드 (v0.4 신규)

서울 열린데이터광장 공식 절차(원문 확인 완료): **열린데이터광장 접속 → Open API 인증키 신청 → API 검색/확인 → API 활용/애플리케이션 제작 → 애플리케이션 등록**. 실시간 지하철 전용 인증키가 아니라 **일반 인증키**를 신청한다.

**활용명 예시**: 프레시매니저 유동판매 추천 서비스 데이터 타당성 PoC
**활용 목적 예시**: 서울시 실시간 도시데이터의 여의도 인구·혼잡도·미래예측·상권현황·날씨 데이터를 수집하여 시간대별 패턴과 예측 활용 가능성을 분석하기 위한 비상업적 개인 PoC

**인증키 보관**: 환경변수(`SEOUL_OPEN_API_KEY`)로만 관리. GitHub 저장소·README·분석 리포트·화면 캡처·오류 로그·대화창에는 절대 넣지 않는다.

**1차 호출 순서**: ① 샘플키로 광화문·덕수궁 호출 → ② 응답구조 확인 → ③ 발급키로 여의도 호출 → ④ 장소코드 확인 → ⑤ 현재 인구 필드 확인 → ⑥ 예측 필드 확인 → ⑦ 상권현황 호출 → ⑧ 날씨 실제·예보 필드 확인 → ⑨ 원본 저장 → ⑩ 필드 대응표 작성. 처음부터 전체 수집기를 만들지 않는다.
