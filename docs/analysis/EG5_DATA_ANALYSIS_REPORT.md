## 3. 분석 방법과 해석 원칙

- 숫자형 원본 값은 raw JSON을 변경하지 않고 분석 시점에만 숫자로 변환했다.
- 인구 중심값은 `(AREA_PPLTN_MIN + AREA_PPLTN_MAX) / 2`로 계산했다.
- 인구 범위폭은 `AREA_PPLTN_MAX - AREA_PPLTN_MIN`으로 계산했다.
- 예측 중심값도 예측 최소·최대값의 평균으로 계산했다.
- 성별·연령·상주 여부 비율은 서울시 추정 집계값이며 개인 단위 정보가 아니다.
- 혼잡도는 공식 범주를 그대로 보존했다. 임의 점수화는 Feature 후보로만 정의하고 아직 적용하지 않았다.
- 단일 시점 결과를 요일 패턴, 반복 피크, 인과관계 또는 판매효과로 일반화하지 않는다.
- 서울시 유동인구는 특정 건물 앞, 지하철 출구 또는 프레시매니저 담당구역의 실제 보행량과 동일하지 않다.

## 4. Raw JSON 구조

### 4.1 최상위 구조

세 raw JSON의 최상위 구조는 동일하다.

| 키 | 형식 | 확인 결과 |
|---|---|---|
| `SeoulRtd.citydata_ppltn` | 배열 | 장소 객체 1개 |
| `RESULT` | 객체 | `RESULT.CODE`, `RESULT.MESSAGE` 포함 |

세 응답 모두 `RESULT.CODE=INFO-000`이다.

### 4.2 장소 객체 구조

장소 객체에는 22개 필드가 존재한다.

- 식별·혼잡: `AREA_NM`, `AREA_CD`, `AREA_CONGEST_LVL`, `AREA_CONGEST_MSG`
- 현재 인구범위: `AREA_PPLTN_MIN`, `AREA_PPLTN_MAX`
- 성별 비율: `MALE_PPLTN_RATE`, `FEMALE_PPLTN_RATE`
- 연령대 비율: `PPLTN_RATE_0`부터 `PPLTN_RATE_70`까지 8개 필드
- 상주 여부: `RESNT_PPLTN_RATE`, `NON_RESNT_PPLTN_RATE`
- 기준 상태·시각: `REPLACE_YN`, `PPLTN_TIME`
- 예측: `FCST_YN`, `FCST_PPLTN`

세 장소 모두 다음 품질조건을 만족한다.

- raw의 장소코드와 공식 대상코드 일치
- raw의 장소명과 승인된 장소명 일치
- 현재 인구 최소값이 최대값 이하
- 성별 비율 합계 100.0%
- 상주·비상주 비율 합계 100.0%
- 연령대 비율 합계는 반올림 오차 범위에서 약 100%
- `FCST_YN=Y`
- 예측 배열 12개
- `REPLACE_YN=N`

`REPLACE_YN`의 업무적 의미는 이번 단일 응답만으로 확대 해석하지 않는다.

| 시간대 기준선 | 동일 장소·요일·시간의 반복 관측 | 평소 수준과 비교 |
| 최근 변화율 | 연속 관측 중심값 | 증가·감소 가속도 확인 |

| 역사적 백분위 | 충분한 장소별 분포 | 현재값의 상대적 희소성 판단 |
| 피크 지속시간 | 연속 고인구 관측 | 일시 피크와 지속 기회 구분 |
| 예측오차 | 예측시점별 후속 관측 | 1·3·6시간 예측 신뢰도 검증 |

### 8.3 별도 승인 데이터가 필요한 Feature

| 데이터 | Feature 예 | 현재 상태 |
|---|---|---|
| 카드소비 기반 상권현황 | 소비활동 단계·변화 | 지원 범위 확인 필요 |
| 날씨 예보 | 실행시점 강수·기온·바람 | 예보와 관측 분리 필요 |

## 9. 유동판매 추천 가능성 판정

### 9.1 확인된 사실

- 장소 간 현재 인구, 혼잡도, 비상주 비율과 미래 경로에 뚜렷한 차이가 있다.
- 동일 시점 비교가 가능하고 예측 배열도 동일한 시간축을 제공한다.
- 인구 기회 크기, 시간창과 혼잡 지속성을 설명하는 Feature를 만들 수 있다.
- 장소별 raw·metadata가 독립 저장되어 추적과 재현이 가능하다.

### 9.2 아직 확인되지 않은 가설

- 인구가 많은 장소에서 실제 판매가 증가하는가
- 비상주 비율이 높은 장소에서 판매 기회가 커지는가
- `붐빔` 상태가 판매에 유리한가, 오히려 운영을 방해하는가
- 예측 피크 전에 이동하는 것이 현장 성과를 높이는가
- 강남역의 높은 절대 인구가 구로·가산보다 높은 순효과로 이어지는가

### 9.3 현재 판정

```text
Feature 구조 타당성: PASS
장소 간 분별력: PASS
Forecast 사용 가능성: CONDITIONAL PASS
추천 성능 검증: NOT YET EVALUABLE
판매효과 검증: OUT OF CURRENT EVIDENCE
```

Forecast는 구조적으로 사용할 수 있지만 실제 예측시점의 후속 관측과 연결해 오차를 확인하기 전에는 추천 의사결정의 신뢰 Feature로 확정할 수 없다.

## 10. 다음 수집에 필요한 데이터

### 10.1 최우선: 예측과 후속 관측 연결

각 수집에서 다음을 보존해야 한다.

- 요청시각
- 관측 기준시각
- 예측 대상시각
- 예측 최소·최대·혼잡도
- 같은 대상시각의 후속 실제 관측 최소·최대·혼잡도

이를 통해 1·3·6시간 리드타임별 예측오차, 예측범위 포함률과 혼잡도 일치율을 계산한다.

### 10.2 시간대와 요일 범위

호출주기는 이번 보고서에서 결정하지 않는다. PM 승인 주기 안에서 다음 구간이 포함되도록 수집 설계를 검토한다.

- 평일 출근 전후
- 평일 점심 전후
- 평일 퇴근 전후
- 저녁과 야간
- 주말 또는 공휴일
- 여러 주에 걸친 동일 시간대 반복 관측

현재 1회 단면만으로는 반복 패턴과 요일 차이를 확인할 수 없다.

### 10.3 데이터 품질

- 장소별 호출 성공률과 연속 실패
- 관측시각 지연 분포
- 예측 배열 개수·시간간격 변동
- `FCST_YN=N`과 예측 결측 구분
- 상권·날씨 데이터의 `not_supported`와 `missing` 구분
- 같은 회차의 장소별 요청시각 차이
- 기존 파일 덮어쓰기와 원본 손상 여부

### 10.4 추천 검증을 위해 별도로 필요한 결과 데이터

실제 추천 유효성을 판단하려면 최소한 다음 중 하나가 별도 승인돼야 한다.

- 프레시매니저의 비식별 집계 판매결과
- 추천 후보에 대한 현장 도달·체류·판매 가능 여부
- 운영자가 기록한 추천 유용성 또는 실행 불가 사유

이 데이터가 없으면 분석 결과는 `유동인구 기회 후보`이며 실제 판매 추천 성과가 아니다.

## 11. 권장 다음 단계

1. 이번 회차의 raw·metadata를 현재 외부 경로에 그대로 보존한다.
2. PM 승인 없이 추가 API 호출이나 실패 재호출을 하지 않는다.
3. 반복수집 진입 전 외장 저장장치 복사 또는 승인된 클라우드 폴더 백업 Gate를 충족한다.
4. API 호출한도와 승인 수집주기를 확정한 뒤 예측-후속관측 연결이 가능한 반복 설계를 검토한다.
5. 초기 규칙 기반 분석에서는 `인구 기회`와 `운영 혼잡 위험`을 별도 Feature로 유지한다.
6. 판매결과 또는 현장 피드백이 승인되기 전에는 추천 점수나 모델 성능을 주장하지 않는다.
